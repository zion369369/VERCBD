# Website assistant and Geoapify

## Server configuration

Set `GEOAPIFY_API_KEY` and `GROQ_API_KEY` in the server environment. Local development uses the ignored `frontend/.env.local`. These values must not use the `NEXT_PUBLIC_` prefix and must not be committed or copied into documentation. Deployment excludes environment files; configure the same variables in the hosting environment. `GROQ_MODEL` optionally selects a supported text model; the tested default is `openai/gpt-oss-20b`.

The provided keys were tested successfully against Geoapify routing, route matrix and reverse geocoding, and Groq model discovery/chat completions. Provider URLs and error bodies are not returned to the browser or logged by these endpoints.

## Assistant knowledge

`npm run dev` and `npm run build` run `scripts/build-chat-knowledge.cjs`. It extracts readable copy from 26 public routes, including the legacy solution pages and story detail pages, plus 12 allowlisted public default collections. It never reads secrets or executes source expressions. The prepared index is `frontend/lib/data/site-knowledge.json`.

Every chat request also reads the current server CMS. Published programs, about text, board/staff details, branches, legal information, reports, awards, partnerships, gallery captions, campaigns, published news/stories and active linked vacancies become searchable. Admin edits are available without rebuilding; changes to hardcoded page copy require the normal dev/build index step.

The explicit allowlist excludes inquiries, CVs, applicant data, subscribers, donor records, credentials, draft news/jobs and temporarily withdrawn microfinance eligibility/process fields. Source links are generated by the application, with duplicate links removed.

Rules handle greetings, contact information, branch counts and lookups, BDJobs recruitment, private-data requests and eligibility restrictions. Weighted retrieval selects relevant public content for other questions. Groq rewrites that content into a conversational English or Bangla answer. The assistant retains short conversation context for follow-ups. Unknown questions receive an honest fallback; provider failures or rejected unsupported numeric claims return the factual rule/retrieval answer.

The widget uses safe React text rendering, accessible labels, visible source links, mobile sizing, Enter/Shift+Enter, Escape, cancellation and new-chat controls. Branding is **Powered by Hellotek**. Conversations are kept in page memory, not written to the CMS. Questions and limited conversation context are sent to Groq only when generating an AI-assisted answer.

## Geoapify location integration

`POST /api/location` accepts `route`, `matrix` or `reverse`. The browser supplies the starting point and known VERC office IDs. The server resolves office coordinates from the authoritative directory, validates inputs, limits requests and calls Geoapify using the server key. Only normalized distance/time/geometry or the nearby street address returns to the browser.

Routes use driving mode, metric units and free-flow traffic. They are not live-traffic ETAs. A matrix checks up to eight nearby offices. Device GPS remains the source of live coordinates; Geoapify calculates road routes and provides a recognizable starting-area label. Poor GPS accuracy is visible, and visitors can correct the starting point on the map.

The selected office is retained during location refresh, search/filter changes and nearby comparisons. Changing to the closest checked branch requires an explicit action. The office name and its road distance appear together above the map. Pin/geometry plausibility checks reject distant snapping and impossible shortcut distances. Requests use bounded temporary memory caches, cancellation, throttling and provider timeouts; location is not written to CMS files. Coordinates pass through the VERC endpoint to Geoapify for these calculations.

Live verification from the screenshot's starting point to Head Office returned **17,435 metres** (displayed **17.4 km**), with a separate Aminbazar route of **6,224 metres**. These are different destinations. Distances always come from the provider response, not fixed display values.
